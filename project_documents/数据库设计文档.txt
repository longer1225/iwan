个人社交博客系统-数据库详细设计文档（V2.0 文档化极致迭代版）
1. 设计总则
1.1 核心架构重构思想（适配迭代版）
针对项目需求持续迭代、结构频繁调整、前期设计存在纰漏、后期高频改配的核心场景，彻底放弃传统关系型数据库范式化约束，采用「PostgreSQL 纯文档化存储 + 专属向量存储」极简架构。依托 PG 原生超强 JSONB 文档能力，替代 MongoDB 独立部署，实现一库搞定所有业务+向量检索，兼顾灵活拓展、数据一致性与运维简洁性：
•	极致文档化，零结构锁死：摒弃传统建表冗余字段拆分，99% 业务动态数据、拓展属性、关联关系、多维配置全部使用 JSONB 文档存储，后续新增功能、修改业务属性，无需改表、无需迁移数据、无需改索引，适配任意迭代调整
•	仅保留刚需关系约束：只对「用户唯一账号、核心主键关联、数据唯一性校验」极少数场景保留结构化字段，杜绝过度范式化，彻底解决关系库改造成本高的痛点
•	业务与向量完全解耦：普通社交、博客、聊天业务全量文档化存储；AI RAG 知识库、文本向量检索数据独立存储，通过 pgvector 插件实现，互不干扰性能
•	单库极简运维：无需部署 MongoDB、MySQL 多数据库，仅依赖 PostgreSQL17，同时支持文档存储、事务约束、向量检索、GIN 高性能检索，适配 Windows 开发环境
•	高容错、易迭代：前期设计纰漏无需重构数据表，仅需增量修改 JSONB 文档内部字段，支持灰度更新、兼容旧数据，适配长期版本迭代
1.2 数据库基础配置（不变兼容）
•	数据库版本：PostgreSQL 17（Windows 64位）
•	字符集：UTF-8
•	插件依赖：pgvector（仅AI向量模块启用）
•	主键策略：全局雪花算法唯一ID（兼容分布式、无自增主键）
•	时间类型：统一 timestamp 带时区
•	核心存储引擎：原生 JSONB 文档引擎（替代独立文档数据库）
1.3 最终存储分层方案（定稿：全文档+刚需结构化+向量）
数据类型	存储方案	适用业务场景	核心优势
刚需结构化数据（仅保留）	PostgreSQL 基础固定字段	主键、用户唯一账号、数据状态、创建/更新时间、逻辑删除标记	保证核心数据唯一、非空、可索引，保留事务基础约束，杜绝数据脏数据
全量业务动态数据（99%）	PostgreSQL JSONB 文档存储（核心主力）	用户拓展信息、好友关系配置、分类标签关联、博客内容、多媒体资源、评论回复、点赞收藏、聊天消息、订阅配置、所有后续新增业务属性	完全无结构束缚，任意迭代修改，无需改表，读写性能优于Mongo，支持索引检索、事务保障
AI向量数据	PostgreSQL pgvector 专属向量字段	博客内容向量化、RAG知识库切片、智能问答相似度检索	业务与AI数据同库隔离，运维简单，向量检索高效，兼容业务主键关联
2. 全局文档化设计规范（新版）
2.1 极简通用字段规范
所有业务表仅保留4个固定结构化字段，彻底精简表结构，所有拓展属性全部下沉至JSONB文档：
•	id：bigint，雪花算法全局唯一主键，非空
•	create_time：timestamp，数据创建时间，非空，默认now()
•	update_time：timestamp，数据更新时间，非空，默认now()
•	is_deleted：smallint，逻辑删除（0-未删除，1-已删除），非空，默认0
强制规范：除以上4个字段，业务表禁止新增任何结构化字段，所有业务属性、关联关系、配置参数全部放入JSONB文档字段
2.2 JSONB文档使用统一规范
•	全业务统一文档字段命名：doc（统一字段名，极简统一，无需区分meta/extra，降低维护成本）
•	所有迭代需求、新增属性、功能修改，仅更新doc文档内部JSON结构，严禁ALTER TABLE改表
•	高频查询、筛选、排序的doc内部key，单独建立GIN索引，保证检索性能不弱于结构化字段
•	doc文档默认值为{}，空数据不存储冗余字段，支持动态增减任意层级JSON属性
2.3 索引规范（适配文档化）
•	所有表主键默认建立唯一索引
•	doc文档内高频检索字段（用户ID、状态、分类、时间等）建立GIN索引
•	彻底取消外键索引、冗余关联索引，减少写入性能损耗
•	仅保留业务刚需检索索引，杜绝过度索引设计

4. 整体&AI模块最终设计思路总结
4.1 全局整体设计核心思路
全程围绕你需求频繁迭代、前期设计有纰漏、后续需持续改配的核心痛点，放弃传统关系型数据库范式枷锁，采用「PostgreSQL 一库统一架构」，不部署MongoDB、向量数据库等独立组件，极简运维、降低开发成本。核心逻辑为：极致文档化兼容迭代，最小结构化保障稳定，专属向量字段支撑AI能力。
所有业务表统一收敛为「4个通用结构化字段+1个JSONB文档字段」，彻底杜绝频繁改表、数据迁移、索引重构问题。所有可变业务属性、关联关系、自定义配置、新增功能逻辑全部放入JSONB，支持灰度迭代、旧数据兼容；仅保留主键、时间、逻辑删除等刚需固定字段，保障数据唯一性、事务性、基础稳定性，平衡了文档库的灵活性与关系库的可靠性。
4.2 AI模块专项设计思路
AI模块是本架构的核心亮点，区别于传统「业务库+独立向量库」的复杂架构，采用同库异构、读写分离、能力解耦的设计思路，完美适配博客社交系统AI场景：
1、文档承载业务，独立字段承载向量，各司其职
AI模块所有可变业务属性（会话配置、切片规则、模型版本、统计维度、消息拓展参数）全部存入JSONB，方便后续新增AI功能、调整RAG策略、升级模型无需改表；向量数据单独使用vector专属字段存储，不混入JSONB，保证向量检索的高性能、高精度，避免文档结构干扰向量计算。
2、场景分层设计，覆盖全AI链路
拆分四张AI核心表，完整覆盖「会话管理-消息交互-知识库向量检索-使用统计」全链路：会话表管理用户对话场景，消息表存储对话上下文，向量表承载核心RAG检索能力，统计表支撑功能迭代优化，结构清晰、职责单一，方便后续模块单独拓展。
3、极致适配迭代，兼容未来拓展
AI行业与功能迭代极快（模型升级、检索算法优化、新增AI创作场景、新增统计指标），本设计无任何硬编码字段、无固定关联约束。后续新增AI能力、调整向量维度、修改切片逻辑、新增对话配置，仅需修改JSONB内部参数，无需改动表结构，完美解决前期设计纰漏、后期频繁优化的问题。
4、极简运维，规避多库弊端
摒弃「业务PG+独立向量库」的部署模式，依托pgvector插件实现同库向量检索，业务数据与向量数据同源、事务一致、运维统一，避免多库同步延迟、部署复杂、数据不一致等问题，极大降低开发与部署成本。
5、贴合博客业务场景
向量数据绑定博客主体内容，通过文档字段关联业务属性，可实现博客智能推荐、内容相似度匹配、AI辅助创作、知识库问答等核心场景，同时保留灵活拓展性，支持后续延伸更多AI智能功能。
4.3 整体架构最终优势总结
1、开发极快：需求变更、功能新增无需改表，前端后端同步迭代，无需适配数据库结构；
2、迭代无压力：前期设计漏洞可随时增量修复，不影响现有数据，支持灰度发布；
3、运维极简：单PG库搞定业务+文档+向量，无需维护多组件、多数据库；
4、性能均衡：结构化字段保障基础检索，JSONB+GIN索引保障业务查询，独立vector字段保障AI检索性能；
5、兼容性强：兼顾关系库事务、一致性、稳定性，同时拥有文档库的灵活拓展性。
